# CodeDNA model card

## Intended use

CodeDNA is a prototype review-support system. Given a developer's historical Python files, it measures whether a new Python submission is behaviourally consistent with that history and shows the largest measurable deviations.

It is intended for demonstration, research and assisted review. It is not intended to determine whether code was generated by AI, prove authorship, detect plagiarism, or make disciplinary decisions.

## Current model state

The application currently uses `deterministic-baseline-v2` unless a trained artifact exists at `codedna/artifacts/fusion_model.json`.

Two trainable challengers consume the same five inputs:

- balanced logistic fusion as the reliability-first baseline;
- a custom `5 → 16 → 8 → 1` ReLU neural fusion head with dropout and L2 regularization.

The selected artifact is whichever achieves the higher mean held-out-author F1; lower Brier score breaks a tie. The five inputs are:

1. lexical similarity;
2. AST-structural similarity;
3. complexity similarity;
4. local AST-token-vector similarity;
5. Surface–Structure Consistency Gap.

The default fourth input is a dependency-free offline representation of AST paths and token relationships. An optional frozen CodeBERT provider is implemented but is not active unless its dependencies, weights and environment configuration are present. Evaluation results must state which provider was used.

## Training data requirements

- one directory per author;
- at least four authors;
- at least six distinct valid Python files per author;
- attributable code with public licensing or contributor permission;
- templates, forks, generated code and copied coursework removed;
- exact content duplicates removed before profile/query splitting.

## Evaluation protocol

- Each author's files are split into enrollment and held-out query files.
- Positive pairs combine an author's profile with that author's held-out query.
- Negative pairs combine the same profile with another author's query.
- Outer folds hold out claimed authors, preventing the fusion model from training on the author it is tested against.
- Report ROC-AUC, F1, precision, recall, false-positive rate and confusion counts.
- Compare the full fusion model with representation-only and engineered-feature baselines.

## Current benchmark evidence

The active artifact uses the AST-token representation and logistic fusion selected against the MLP challenger. The leakage-free, held-out-author public benchmark contains four commit-pinned repository-owner proxy labels and 253 eligible files. At the conventional 0.50 comparison threshold it achieved ROC-AUC 0.741, F1 0.701, precision 0.678, recall 0.808 and false-positive rate 0.521. The deployed three-way thresholds are calibrated separately: the Consistent threshold is 0.9358, producing a held-out impostor-consistent rate of 0.105 and consistent-case recall of 0.329. It sends 61.2% of pairs to Uncertain. This abstention policy lowers false reassurance but does not make the prototype suitable for disciplinary use. Exact results and fold variance live in `work/evaluation/results.json`.
## Limitations

- A developer can change style because of learning, collaboration, a framework, refactoring or a new task domain.
- A historical repository may contain mixed authorship.
- The current profile ignores time and treats history as one distribution.
- Python-only signals do not transfer directly to other languages.
- Small hackathon datasets produce uncertain estimates with high variance.
- The local AST-token representation is not a pretrained semantic model.
- A low score indicates deviation, not its cause.

## Human oversight

Every report must retain this meaning: behavioural deviation is evidence to review, not proof of AI use, plagiarism or misconduct. Reviewers should inspect the highlighted features, code history, task context and the developer's explanation before taking action.

## Explanation scale

Feature explanations use a bounded deviation index. When historical variance is sufficiently large, the denominator is the historical standard deviation. For nearly constant features, the system uses a documented stabilizing scale rather than presenting an unstable or infinite z-score. The UI caps the displayed magnitude at 9.9 while retaining the uncapped value in the evidence JSON for ordering and audit.
